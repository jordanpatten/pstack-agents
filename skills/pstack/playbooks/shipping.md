### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** Merging is irreversible, so this playbook runs only on an explicit request to merge, land, or ship.

1. **Verify each PR independently before it lands.** One verifier per PR, a fresh subagent that did not write the code, runs the change the way a user would on the real surface, parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. A PR whose branch neither holds nor needs that code can move onto trunk and land on its own, but it needs a fresh verdict first, because its old one ran with that code beneath it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before you trust an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Report each kind of noise with its files. The changed part still gets fresh checks and a review. A lane with no build output, such as a dev server, cannot show this, so rerun it.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR (`gh pr merge <pr> --squash`). A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base. Arm `--auto` only on a PR whose verdict covers its current head. After a merge lands, retarget the next PR to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The patch-id rule in step 3 decides whether its verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base. Watch the run with `gh pr checks --watch` under a polling loop (`/loop` where available, see `../harness.md`) until the ceiling reads merged. A base that moves to trunk when its parent merges is expected. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
